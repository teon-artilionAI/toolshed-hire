# Deviations from the Task 1 design document

Every place I know of where the built system differs from the Task 1 design
document, and why. I found them in the pull request descriptions, the backend
and frontend READMEs and the code. Each pull request also has a "Self review"
section that records these decisions at the moment I made them.

## Hosting and operations

| What the design planned | What I built | Why |
|---|---|---|
| The database region was left open between London and Frankfurt until a round trip had been measured, and the API was to sit beside it. | The API runs on Cloud Run in `europe-west2`, London, and the database on Neon in AWS `eu-west-2`, London. | A request makes several database round trips and only one back to the browser, so the API belongs beside the database. London is a dearer Cloud Run price tier than Belgium, and I accepted that. |
| Production capped at four instances, with a pool of five connections each, which is the connection ceiling the scalability requirement is worked out from. | Both environments are capped at one instance. | The system runs on a free trial, and an instance cap is the only hard limit on what a public service can cost if somebody floods it. One instance at a concurrency of 80 is far more than a demonstration needs. The workflow records the design figure, and a paying client means setting it back to four. |
| A billing budget with alerts in rand. | A budget of 30 USD with alerts at 20, 50 and 100 percent. | The billing account and its free trial credit are in US dollars, and a budget is set in the currency of its billing account. |
| The image cleanup policy keeps the two newest images and the one serving production. | It keeps the three newest and deletes the rest once they are seven days old. | A cleanup policy cannot name the image that is serving, so I keep one more instead. Storage stays under the free allowance, and [OPERATIONS.md](../../infra/OPERATIONS.md) has the command I use to check it. |
| Scheduled checks every five and every thirty minutes to measure availability over trading hours. | No scheduled checks. Each deployment smoke tests the new revision and checks the deployed headers, and I check the health route by hand. | A scheduled request every few minutes would keep the API and the database awake all day, which defeats scaling to zero and spends the trial credit. I still want the availability figure, so this is open for Task 3. |
| Production holds the business's own records, with the open bookings carried across from the paper diary. | The seed loads a fictional fleet of 400 units, five accounts, the worked example and a season of trading history into every environment, production included. The season is 1,613 closed hires from June to September 2026 at the three branches, with late returns and damage that was resolved, and it writes no audit events. The seed runs on every deployment and only creates what is missing. Customer accounts have their own seed password. | This is a demonstration with no real business behind it, so production needs a fleet and accounts from its first deployment, and the report needs a history to say anything. The application did none of the season's work, so the audit trail holds only what happened on the system itself. The separate customer password lets me publish one customer login without exposing the staff ones. |

## Repository and pipeline

| What the design planned | What I built | Why |
|---|---|---|
| A private repository. | The repository is public. | The submission is the link to this repository, so my lecturer has to be able to open it without an invitation. Every account specific value in [infra](../../infra) is a placeholder, and the API's own address is masked in the workflow logs. |
| A preview of the frontend and a staging revision of the API for every pull request, with a short lived database branch. | Staging is deployed on every merge into `develop`. Every pull request runs the browser tests against the real API and a freshly seeded PostgreSQL inside the pipeline. | The browser tests in the pipeline already prove each pull request against a real API and database, without the extra secrets, database branches and allowances a preview per pull request would need. |
| A browser smoke suite after each deployment, and the smoke suite run against the production candidate. | After every staging deployment the customer, counter and admin journeys in [release-journeys.spec.ts](../../frontend/e2e/release-journeys.spec.ts) run in a browser against the staging site, with no trace and no video. Production gets the health smoke test on the candidate and through the site, and both get the header and TLS check. | The journeys book, check out and take back real units, so they run where that does no harm and never against production. A trace or a video would record the passwords the journeys type. The candidate is proved healthy with its database before it takes any traffic. |
| An automated header and TLS scan with every release. | [check-security-headers.sh](../../infra/scripts/check-security-headers.sh) runs after every deployment to staging and to production. It checks the headers on the page and on an API answer through the rewrite, HSTS of at least half a year (15,768,000 seconds) among them, that plain HTTP is redirected, and that TLS 1.1 is refused while a TLS 1.2 control connects, both probed with `openssl s_client`. | Running it after every deployment costs seconds, and a header lost in a change to `vercel.json` then fails the deployment that lost it instead of waiting for a release. |
| Release branches named after each task. | The releases before the end of Task 2 are named after their version, `release/0.1.0` to `release/0.3.0`. The Task 2 release branch is `release/task-2` and carries the version `0.4.0`, and the tag `task2-v1.0` marks the state I hand in. | Task 2 was delivered in four releases, and a version number says which. The last of them closes the task, so its branch carries the task's name. |
| Every migration rehearsed on an empty database, on a seeded one and as a downgrade before it reaches production. | Every pull request migrates an empty database and every merge migrates the seeded staging database. I rehearsed the downgrade by hand for the first migrations only. | A rollback never runs a downgrade. Each migration is written to work with the revision still serving, and a migration that is itself wrong is fixed forward with a new one, as [OPERATIONS.md](../../infra/OPERATIONS.md#rollback) says. |
| High and critical advisories block a merge. | They still do, unless [audit-exceptions.json](../../frontend/audit-exceptions.json) holds a reviewed exception for that one advisory, with a reason and an expiry date. One does, for `braces`. | A high advisory against every version of `braces` was published while a pull request was in review, and blocked every merge. It reaches the build only through Tailwind CSS 3 expanding my own file patterns, and nothing from it is in the bundle. The only fix is the move to Tailwind 4, tracked in issue [#49](https://github.com/teon-artilionAI/toolshed-hire/issues/49), and Dependabot's Tailwind 4 update ([#37](https://github.com/teon-artilionAI/toolshed-hire/pull/37)) is closed in favour of it. Every other advisory still blocks, and this one blocks again when the exception expires. |
| The browser tests run on the real clock. | The pipeline starts the API's clock at 10:00 in Cape Town on the day of the run with `TEST_BUSINESS_TIME`. The journeys on staging run on the real clock, so after closing time the counter journey books two days ahead and the customer cancels it. | A hire can only start today while the branch is open, so the counter journey would fail whenever the pipeline ran after 17:00. The setting is refused by every environment except test, so no deployed service can run on a clock that lies. Two days ahead and not one, because cancelling tomorrow's booking after 17:00 would count as a late cancellation against the customer. |
| ESLint and the TypeScript compiler with the `any` type banned outright, and strict mypy. | Oxlint in place of ESLint, with a rule that bans `any`, and TypeScript's strict mode set explicitly in the configuration. Strict mypy everywhere, with the check on an explicit `Any` switched off only in the modules that declare pydantic models. | The prototype from Task 1 was already set up with Oxlint, which has the React and TypeScript rules I need, so I kept one linter rather than adding a second. pydantic makes mypy invent a hidden member typed `Any` on every model, and the check reports it against my class. Narrowing the exception to those modules keeps it live everywhere a hand written `Any` would matter. |

## Data model

| What the design planned | What I built | Why |
|---|---|---|
| No column for late cancellations. | `customer_profile.late_cancellation_count`. | A late cancellation has to be recorded on the customer's profile, and the column list had nowhere to put it. |
| No columns for the email verification and password reset tokens. | `user_account` holds the SHA-256 of each token and when it expires, with unique partial indexes. | Each link needs a single use, time limited token, and only its hash may be stored. |
| No column for the counter's damage flag on a returned unit. | `rental_item.flagged_for_damage`, a boolean added by migration `0006` with a default of false. | The only other place the schema offers is the free text of the notes, and the deposit should not depend on matching words in free text. A column with a constant default is added without rewriting the table. |
| The indexes of the baseline. | Migrations add indexes and nothing else. [0003](../../backend/alembic/versions/0003_customer_phone_search_index.py) and [0004](../../backend/alembic/versions/0004_counter_overview_indexes.py) for the counter's customer search, asset locator and diary, [0005](../../backend/alembic/versions/0005_damage_report_indexes.py) for damage reports, [0007](../../backend/alembic/versions/0007_report_indexes.py) five for the report, [0008](../../backend/alembic/versions/0008_admin_log_indexes.py) four for the audit trail and the notification log, [0009](../../backend/alembic/versions/0009_admin_catalogue_index.py) one for the models of a category, [0010](../../backend/alembic/versions/0010_asset_register_indexes.py) two for the asset register, [0011](../../backend/alembic/versions/0011_people_list_indexes.py) three for the lists of staff and customers, and [0012](../../backend/alembic/versions/0012_rate_limit_window_index.py) one on `rate_limit_counter` for pruning old counters. | Each new read needed an index the baseline did not have, and a test asks PostgreSQL for its plan and proves each is used. Those tests caught my first version of `0010`, whose index pulled the availability search off its GiST index, so that index is partial. |
| `no_show_count` as a rolling count over twelve months. | `no_show_count` is a running total, and the three strikes rule counts the no shows of the last twelve months from the reservations themselves. Releasing a customer from hold keeps the count. | A rolling figure in a column goes stale as days pass without anything writing to it. Counting from the reservations is always right and stands on an index. The count is history, and the hold is the owner's decision about it. |
| A charge reversed by a correction takes the status `REVERSED`. | A reversal is a new charge of the same type with every amount negated, pointing at the original through `reverses_charge_id`. The original stays `SETTLED`, and `REVERSED` is never written. | A settled charge is never edited, and marking it reversed would be an edit. The negative row nets it off in the totals and in the report. |

## Security and sessions

| What the design planned | What I built | Why |
|---|---|---|
| The lockout counts failures in the account's own columns, and `rate_limit_counter` serves the throttles. | Each wrong password is also counted in `rate_limit_counter`, to the second, under a salted hash of the account, and the account locks on the fifth failure inside the last fifteen minutes. The lazy sweep prunes old `rate_limit_counter` rows, at most 500 at a time in one statement, on the index migration [0012](../../backend/alembic/versions/0012_rate_limit_window_index.py) adds, and sign in deletes nothing itself. `refresh_session` rows are not pruned. | A window of fifteen minutes needs the time of each failure, and the account row holds only a number. The first version counted consecutive failures, and I corrected it to a sliding window without adding a table or a column. Pruning on the sweep keeps the table small without a scheduled job, and keeps an unbounded delete off the sign in path. The application role holds no DELETE on `refresh_session`, so its old rows wait for an operator job, which [backend/README.md](../../backend/README.md#throttling) describes. |
| A 128 bit refresh token. | A 256 bit refresh token. | It costs nothing and is stronger. |
| The role on the access token trusted for up to fifteen minutes, read again on refresh and on the three operations that matter most. | Every request reads the role and whether the account is active from the database. | It is stricter, and the cost is one indexed read. A role change or a deactivation reaches the person's next request, not their next refresh. |
| Throttling on the account routes, with no numbers set. | Seven limits with defaults of my own, listed in [backend/README.md](../../backend/README.md#the-throttles-of-the-account-routes). They can be lowered in a deployment and never raised. | The design named the routes and not the figures. |
| A password reset revokes every session. | It does, with the revocation reason `LOGOUT`, and the audit event says it was a reset. | The enumeration of reasons had no closer match, and adding one was not worth a migration. |
| The owner creates, edits, deactivates and reactivates any account, and never reads or sets a password. | A new staff account is opened with a password nobody knows and sent the reset link every account uses, so the person chooses their own. The last active administrator can never be deactivated or moved to another role, and an administrator cannot deactivate their own account. Every write of user management first locks every active administrator. A completed reset verifies the email, so a new staff account ends verified once its owner sets a password. | The reset link already does what a first password needs, with no new kind of token, and it only ever goes to the account's own address, which is all a verification link proves. Without the rule about the last administrator the business could lock itself out of its own system, and the lock means two administrators demoting each other at once cannot leave it with none. |

## Email

| What the design planned | What I built | Why |
|---|---|---|
| Email delivered to every customer. | Restricted mode. `EMAIL_ALLOWED_RECIPIENT` names the only address the service sends to, the adapter refuses any other before the provider is called, and a refused message is never redirected. The session carries `emailDeliverable`, so the screens say when an email cannot be delivered instead of promising one. | The demonstration has no verified sending domain. Refusing on the server stops a stranger's address from ever receiving mail from a university project, and redirecting would hand one customer's booking to somebody else. |
| The confirmation sent after the commit. | It is sent after the commit, inside the same request, with an idempotency key, and the account messages are sent the same way. | Cloud Run only gives a container CPU while it serves a request, so work left for a background thread might never run. The key means a message dispatched twice is delivered once. |
| Three outbound messages. | Two more. A short note to the owner of an address that somebody tried to register again, which carries no token and writes no notification row, and the message a new member of staff is sent with their reset link. | Registration answers every address the same way, so the form cannot reveal who has an account, and the note tells the real owner what happened. A new member of staff needs the link to choose a password. |
| A customer re-sends their own confirmation from SC-08, counter staff for their branch, and the owner for any. | The owner sends a failed confirmation again from SC-24. The re-send is a new notification row through the same outbox, linked to the failure through its audit event, and the failed row is never changed. | With email restricted to my own address, a re-send by a customer or the counter could only fail again, so I built the owner's, where the log shows the failure beside it. The customer's and the counter's re-send are left for Task 3. |

## Business rules

| What the design planned | What I built | Why |
|---|---|---|
| Counter staff may book for today, and customers from today onwards. | Nobody can start a hire today once the collection branch has closed. | After closing nobody can collect, and the no show sweep would mark the booking a no show at once with a strike against the customer. |
| A customer on hold is refused a new booking with an explanation. | Every hold, from three no shows or set by the owner, and a blacklisting get one neutral refusal. It says the account is on hold and to contact a branch, and names no cause. | The owner can now put a customer on hold by hand, and a refusal that spoke of bookings not collected would be wrong for that customer. The reason is the owner's to explain. |
| Opening hours that differ on a Saturday, and no trading on a Sunday. | Each branch has one opening and one closing time, seeded as 07:00 to 17:00, and every day of the week is treated the same. | The branch table in the design holds one pair of times. Hours by weekday need a schema change, and I have listed it as a known limitation. |
| A late fee per day that attracts VAT. | The late fee per day is an amount including VAT. R240.00 is written as R208.70 plus R31.30. | It is the only reading under which the figures of the worked example add up. |
| Hire revenue attributed to each unit, so gross contribution can be reported per unit. | On a hire of one unit the hire charge belongs to that unit. On a hire of more units it is raised on the rental, and the report shares it across the units in proportion to their booking lines, with the rounding cent on the last unit. | The charge is written from the figures stored on the reservation and never worked out again. The share is a policy in the domain, and the shares always add up to the charge. |
| Release reasons for a booking that is returned, cancelled, not collected, expired or reallocated, and none for a loss. | The allocation is released with the reason `RETURNED` before the unit moves to `LOST`, and the audit event says what happened. A lost unit reads as closed with no condition recorded. | The release reasons have no member for a loss, and a unit may not be marked lost while it holds a booking. |
| The owner force releases an allocation with a mandatory reason. | The allocation is released with the reason `REALLOCATED`, and the owner's reason is in the audit event. The booking is then short of a unit and cannot be confirmed or collected until staff find a replacement through the same path as a hold. | The release reasons have no member for a release by hand, and the booking's next step is a replacement unit, which is what `REALLOCATED` means. |
| A later correction to a settled rental is a reversing charge, never an edit. | A settled hire stays settled and takes only a correction that gives money back, a reversal or a negative adjustment, which is refunded at once. A correction that would ask for more is refused with 409. | Asking a settled hire for more would reopen it. Money found owed after settlement is a matter for the office and not for the rental. |
| An overdue hire goes back to partially returned as units come in. | A hire with any unit still out past its due date stays `OVERDUE` until that unit is back. | A hire that still has a late unit is still overdue, and the overdue list should keep showing it. |
| Expired holds and no shows swept on reads and on the first signed in request of the day. | A bounded batch of 25 is swept before every hold, confirmation, read of reservations, availability search, counter read, report and dashboard, and each use case also lapses the one reservation it is about to decide on. | A hold lasts thirty minutes, so a lapse has to be seen before anything an expired hold could wrongly block or allow. A bounded batch keeps the cost of each request flat however many are due. |
| A damage report created at the return itself, quarantining the unit at once. | The return quarantines a unit at once when it comes back a grade worse or flagged, in the transaction of the return, and the damage report is filed as a second step on SC-16. The deposit waits until every such unit has its report, and filing the last one settles it. | The unit leaves availability the moment it is back either way. A report needs an explicit decision on the charge and an amount checked against the replacement value, so it is its own step, and the deposit waits for it rather than being settled on a guess. |
| A damage photograph stored in a private bucket in `us-central1`. | No photograph upload and no bucket. `photo_path` stays empty and SC-16 does not offer one. | The report, its charge and the quarantine stand without a photograph. The upload with its controls C-29 to C-31 is planned for Task 3. |

## Reporting

| What the design planned | What I built | Why |
|---|---|---|
| Utilisation and gross contribution worked out in one query with window functions. | Three statements read each unit's facts for the period, and the day counting, the grouping, the ranking and the paging happen in pure functions of the domain and the application layer. Days out of service are rebuilt from damage reports, losses and the `asset.status_changed` events every move of a unit writes. | Each definition has one copy that is tested with no database. At four hundred units it takes a few milliseconds. [backend/README.md](../../backend/README.md#the-utilisation-report-and-the-admin-dashboard) says how it moves into PostgreSQL, and then into a table of daily figures, as the fleet grows a hundredfold. |
| Every export cell that begins with `=`, `+`, `-` or `@` is escaped. | Those, a tab and a carriage return are escaped with a single quote. A cell that is a plain decimal number, such as `-180.00`, is written as it is, and `-1+2` is still escaped. | No spreadsheet runs a plain number as a formula, and the owner needs negative amounts to add up. |

## Screens and the API

| What the design planned | What I built | Why |
|---|---|---|
| The model page shows a fourteen day availability strip for each branch. | SC-03 says for each branch whether the quantity is free for the dates chosen, beside the price for those dates. | The customer has already chosen dates by then, and one clear answer for them is what the search exists to give. |
| The counter can pick a specific unit or let the system allocate one. | SC-13 always lets the server allocate. | One allocation path keeps the lock and the constraint in one place. The tags of the units set aside are shown once the booking is held. |
| The counter dashboard lists bookings that need a unit swapped. | SC-10 has no such panel. A booking left short by a force release says so on its checkout, SC-14, which offers to find a replacement unit. | A unit is only taken from a booking by the owner's force release, and the booking cannot be collected until it is whole, so the checkout is where staff meet it. |
| SC-21 also resolves damage reports and force releases an allocation. | SC-21 links each open damage report to SC-16, where the owner resolves it, and the force release is on the checkout, SC-14. A booking SC-21 names when it refuses a retirement links there. | Each action sits on the screen that already shows what it changes, the report on the damage screen and a booking's units on its checkout. |
| A quote that applies the customer's trade discount. | The public quote route applies none. The booking applies the discount on the customer's profile. | A public route cannot also depend on a signed in role, because the application refuses to start on a route that declares both. |
